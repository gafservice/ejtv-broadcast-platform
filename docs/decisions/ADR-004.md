# ADR-004 — Evolución hacia ENGINEERING NOC

**Estado:** Aprobado

**Fecha:** Julio 2026

**Versión:** 1.0

**Tipo:** Architecture Decision Record (ADR)

---

# Contexto

La plataforma nació con el objetivo de construir una infraestructura abierta para la distribución profesional de video sobre redes IP utilizando tecnologías abiertas, modulares y ampliamente adoptadas como Linux, FFmpeg y MediaMTX.

Durante las primeras etapas del proyecto se desarrolló exitosamente el núcleo de streaming, incorporando soporte para los principales protocolos de distribución:

- RTMP
- SRT
- HLS
- WebRTC
- RTSP

Adicionalmente se implementaron:

- API de MediaMTX
- Dashboard inicial
- Monitoreo básico
- Automatización de pruebas
- Documentación técnica
- Arquitectura por capas

Con la plataforma funcionando de manera estable, surgió una necesidad que inicialmente no formaba parte del alcance original:

Disponer de herramientas que permitieran comprender completamente el comportamiento interno del servidor y del motor de streaming sin depender de múltiples herramientas independientes del sistema operativo.

Hasta ese momento el diagnóstico requería utilizar diversas utilidades como:

- htop
- iostat
- iftop
- journalctl
- tcpdump
- ip
- ss
- smartctl
- curl

Esto obligaba al ingeniero a abandonar continuamente el Dashboard para localizar la causa de un problema.

Después del análisis técnico realizado durante la planificación del proyecto, se concluyó que la siguiente etapa debía concentrarse en construir una plataforma de ingeniería antes de desarrollar funcionalidades comerciales.

---

# Decisión

A partir de esta decisión, el proyecto evoluciona hacia el desarrollo del **ENGINEERING NOC (Network Operations Center)**.

El ENGINEERING NOC será el núcleo técnico de observabilidad, diagnóstico y administración de toda la plataforma Broadcast IP.

No reemplaza la arquitectura existente.

La amplía.

Toda la funcionalidad desarrollada hasta el momento permanece vigente.

El ENGINEERING NOC será construido de forma incremental sobre la plataforma existente.

---

# Objetivo Principal

Construir una consola de ingeniería capaz de permitir que un ingeniero pueda administrar, comprender y diagnosticar una infraestructura profesional de distribución Broadcast IP desde una única consola.

La plataforma deberá reducir al mínimo la necesidad de utilizar herramientas externas durante la operación diaria.

---

# Visión

La plataforma debe permitir que un ingeniero pueda diagnosticar la gran mayoría de los problemas de una infraestructura Broadcast IP sin abandonar la consola del ENGINEERING NOC.

Ante situaciones como:

- La señal se congela.
- El bitrate disminuyó.
- Un cliente no puede conectarse.
- Existen pérdidas de paquetes.
- Aumentó la latencia.
- El Publisher dejó de transmitir.
- El servidor presenta alta carga.

El ingeniero deberá encontrar la causa observando únicamente la información presentada por el ENGINEERING NOC.

---

# Filosofía de Evolución

A partir de esta decisión el desarrollo seguirá tres grandes etapas.

---

# Primera Etapa — Observabilidad

Primero debemos comprender completamente el sistema.

Esta etapa incorpora:

## System Engineering

- CPU
- Memoria
- Disco
- Interfaces de red
- Servicios
- Estado del sistema operativo

## Streaming Engineering

- Publishers
- Readers
- Paths
- Bitrate
- Codecs
- Resoluciones

## Session Engineering

- RTT
- ACK
- NAK
- Retransmisiones
- Buffers
- Loss
- Flight Size
- Link Capacity
- Bytes
- Packets

## Diagnostics

Interpretación técnica de toda la información disponible.

---

# Segunda Etapa — Portabilidad

Una vez comprendido completamente el sistema, la plataforma deberá instalarse sin modificaciones sobre diferentes infraestructuras.

Entre ellas:

- Servidores físicos
- Máquinas virtuales
- RACSA
- ICE
- AWS
- Otros proveedores compatibles
- Infraestructura local

La plataforma descubrirá automáticamente:

- CPU
- Memoria
- Interfaces
- Discos
- Sensores
- Servicios disponibles
- Capacidades del sistema

El software nunca dependerá de:

- nombres específicos de interfaces;
- cantidad fija de núcleos;
- cantidad fija de discos;
- hardware determinado.

El sistema deberá adaptarse automáticamente al entorno donde sea instalado.

---

# Tercera Etapa — Tolerancia a Fallos

Una vez alcanzadas la observabilidad y la portabilidad, la plataforma evolucionará hacia una arquitectura resiliente.

Esta etapa incorporará:

- Backup
- Mirror
- Replicación
- Health Checks
- Failover
- Recuperación automática
- Monitoreo de nodos
- Sincronización de configuración

El objetivo es garantizar la continuidad del servicio ante la pérdida de un servidor.

---

# Roadmap Estratégico

El ENGINEERING NOC queda estructurado de la siguiente manera:

- ENG-001 — System Engineering
- ENG-002 — Network Engineering
- ENG-003 — Streaming Engineering
- ENG-004 — Session Engineering
- ENG-005 — Diagnostics
- ENG-006 — Resilience Engineering

Las futuras funcionalidades comerciales se desarrollarán posteriormente como módulos independientes.

---

# Principios de Ingeniería

A partir de esta decisión se establecen los siguientes principios permanentes.

## 1. No romper funcionalidades existentes

Toda nueva funcionalidad deberá integrarse preservando el comportamiento actual de la plataforma.

---

## 2. Compatibilidad hacia atrás

Los modelos existentes deberán continuar funcionando aun cuando sean ampliados con nuevas capacidades.

---

## 3. Arquitectura por expansión

Las nuevas capacidades se agregarán mediante nuevos módulos.

No mediante reemplazo de componentes estables.

---

## 4. Preservar toda la información técnica

Toda la información disponible será capturada y almacenada en el modelo interno.

La interfaz decidirá qué mostrar.

Nunca se eliminará información técnica únicamente por razones de presentación.

---

## 5. Separación de responsabilidades

La arquitectura deberá mantener claramente separadas las siguientes capas:

- Recolección de información
- Modelos de dominio
- Servicios
- Diagnóstico
- Presentación

---

## 6. Descubrimiento automático

La plataforma descubrirá automáticamente las capacidades del servidor.

Nunca asumirá una configuración fija del hardware.

---

## 7. Diagnóstico basado en evidencia

El motor de diagnóstico emitirá conclusiones únicamente a partir de métricas verificables.

No se basará en suposiciones.

---

## 8. Documentación continua

Toda decisión arquitectónica relevante deberá quedar documentada mediante un Architecture Decision Record (ADR).

---

# Alcance de la siguiente fase

Durante las próximas etapas el esfuerzo de desarrollo se concentrará exclusivamente en el ENGINEERING NOC.

Quedan expresamente fuera del alcance inmediato:

- Portal de clientes
- Facturación
- Gestión comercial
- Administración de planes
- Paneles para usuarios finales

Estas capacidades serán desarrolladas únicamente cuando la plataforma de ingeniería alcance un nivel de madurez adecuado.

---

# Impacto

Esta decisión no modifica la arquitectura existente.

No reemplaza componentes.

No elimina funcionalidades.

El ENGINEERING NOC será construido sobre la plataforma actual mediante una evolución incremental y completamente compatible con los módulos existentes.

---

# Conclusión

Esta decisión marca el inicio de una nueva etapa del proyecto.

La prioridad deja de ser únicamente distribuir video.

La prioridad pasa a ser comprender, diagnosticar y administrar profesionalmente toda la infraestructura de distribución Broadcast IP.

La evolución tecnológica del proyecto seguirá el siguiente orden:

1. Observabilidad.
2. Portabilidad.
3. Tolerancia a fallos.

Este orden garantiza que la redundancia y la alta disponibilidad se construirán sobre una plataforma previamente comprendida, medible, reproducible y validada.

---

# Frase Rectora del Proyecto

> **No estamos construyendo únicamente una plataforma para transmitir video. Estamos construyendo una plataforma de ingeniería capaz de comprender, operar, diagnosticar y garantizar la distribución profesional de video sobre redes IP.**

---

# Estado

**ADR aprobado y adoptado como guía de arquitectura del proyecto.**
